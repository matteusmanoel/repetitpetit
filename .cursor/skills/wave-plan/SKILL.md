# Wave Plan

Translate the ticket set from `/to-tickets` into a written execution plan the orchestrator can follow without supervision. Output: `docs/slice-n/WAVES.md` + contract doc stubs.

**This skill is user-invoked only.** Do not call it automatically. Do not proceed to dispatch after running it — wait for explicit human approval of WAVES.md.

## 1. Read inputs

Fetch all tickets in scope:
- GitHub: `gh issue list --label ready-for-agent --json number,title,body` (or filter by milestone/label for the slice)
- Local: read all files under `.scratch/<feature-slug>/issues/`

For each ticket, note: blocking edges, cohesion tag (`[standalone]`, `[wave-dependent]`, `[one-shot-recommended]`), and the resources it mentions writing (tables, feature folders, API routes, exported symbols).

If cohesion tags are missing (tickets pre-date the to-tickets patch), classify them now using the same heuristics from `to-tickets` § 3.5.

Also read: `docs/slice-n/` for any existing contract docs, and run `list_migrations` via Supabase MCP if available to capture the current migration baseline.

## 2. Build execution DAG

Map blocking edges into a directed graph. Identify the **frontier** — tickets with no open blockers. This is Wave 1.

Advance iteratively: close Wave N tickets (hypothetically), compute newly unblocked tickets → Wave N+1. Repeat until all tickets are assigned to a wave.

One-shot groups are a **single node** in the DAG — dispatched together, closed together.

Draft vs. active distinction: if a ticket is on the frontier but its blocker PR is open (not yet merged), mark it `Wave N — pending blocker #PR`. The orchestrator activates it only after that PR merges.

## 3. Build ownership matrix

For each ticket, identify what it **writes**:
- Schema tables and migration files (note the new migration filename the ticket will add)
- Feature folders and files (`features/`, `app/api/`, `lib/`)
- Exported TypeScript symbols consumed by downstream tickets

Flag **single-writer conflicts**: any resource written by more than one ticket **in the same wave**. Resolve by either:
- Adding a blocking edge (serialize them across waves), or
- Collapsing into a one-shot group (if cohesion test passes)

Document unresolved conflicts as open questions for human review.

## 4. Draft context contracts

For each wave anchor or one-shot group that **exports an interface consumed by later tickets**:

1. Create `docs/slice-n/<NN>-contract.md` using this template:

```markdown
# <NN> — Contract: <subsystem name>

## Lifecycle
<what this subsystem does; when it is active>

## RPC / API surface
<exact function signatures, route paths, or SQL RPC names this ticket exposes>

## TypeScript exports
<the types and functions downstream tickets import — include the import path>

## Allowed callers
<which tickets or modules may call these>

## Forbidden behaviors
<what downstream tickets must NOT do>

## Integration notes per downstream ticket
- **#N (title)**: <what it needs from this contract>
- **#M (title)**: <what it needs from this contract>
```

2. Add a `Contract doc: docs/slice-n/<NN>-contract.md` line to the body of every downstream ticket that consumes this interface (update the GitHub issue or local file).

## 5. Classify cloud vs local

For each ticket, mark:
- **cloud-safe**: no MCP calls needed during implementation; migration files committed but not applied
- **requires-local-orchestrator**: needs Supabase MCP, MP MCP, or Context7 during or immediately after merge

Build the **MCP Handoff Schedule**: after which wave closures the orchestrator must run which operations (reference `docs/agents/cloud-dispatch.md` § After agents finish for the operation list).

## 6. Define wave gates

For each wave, write the gate conditions — **all must be true** before Wave N+1 can dispatch:
- CI green on `develop` after all Wave N PRs merge
- MCP handoffs from the schedule executed
- Integration gate passed: `pnpm typecheck && pnpm lint && pnpm build && pnpm test`
- Human checkpoint: required for waves touching payments, RLS policies, or production schema changes; otherwise light (30-second confirm)

## 7. Write WAVES.md

Output `docs/slice-n/WAVES.md` with this structure:

```markdown
# Slice N — Execution Plan

_Generated by `/wave-plan`. Human-approved before dispatch._

## Wave 1 — <name>
**Tickets**: #N [standalone], #M [standalone], one-shot: #P + #Q [one-shot-recommended]
**Ownership**:
| Ticket | Writes |
|---|---|
| #N | `features/X/`, migration `YYYYMMDDHHMMSS_x.sql` |
| #P + #Q | `features/Y/`, `lib/supabase/types.ts` (zone Y) |

**Single-writer conflicts**: none / #N and #M both write `lib/X.ts` — serialized by blocking edge
**Gate**: CI green + `generate_typescript_types` executed + [smoke test if applicable]
**Human checkpoint**: no / yes — reason

## Wave 2 — <name>
...

## MCP Handoff Schedule
| After wave closes | Operation | Tool |
|---|---|---|
| Wave 1 | Apply migration + generate types | Supabase MCP |
| Wave 3 | MP homologation smoke | Mercado Pago MCP → `quality_checklist` |

## Human Checkpoints
| Wave | Level | Reason |
|---|---|---|
| Wave 1 gate | Light | No payment/RLS changes |
| Wave 3 gate | Required | First payment webhook live |

## Contract docs
| Contract | File | Consumed by |
|---|---|---|
| Hold Session RPCs | `docs/slice-n/SN-02-contract.md` | #N, #M, #P |

## Open questions
_Items requiring human decision before dispatch can proceed:_
- [ ] <question>
```

**Completion criterion**: every ticket is assigned to exactly one wave; every single-writer conflict is resolved or flagged; every downstream ticket references its upstream contract doc; every wave has explicit gate conditions; Open questions section is empty or all items are marked as deferred with owner.

## 8. Present and confirm

Show the operator:
1. The full WAVES.md (or a summary if > 60 lines — offer to show full on request)
2. List of contract doc stubs created
3. List of open questions requiring decision

Ask:
- Do the wave boundaries feel right?
- Are the one-shot groups correct?
- Any human checkpoints missing or over-specified?
- Any open questions you can resolve now?

Allow up to **2 revision rounds**. If unresolved items remain after 2 rounds, document them in WAVES.md → "Open questions" with `[deferred — owner: human]` and proceed with approval for everything else.

**Do not dispatch any cloud agents.** Dispatch is `/orchestrate`'s job, after the operator explicitly approves this plan.
